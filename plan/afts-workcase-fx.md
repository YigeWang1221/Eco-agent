# Work case：FX 区间预测模板

状态：草案，待用户确认。未施工。日期：2026-10-21。

产品目标见 [afts-base.md](afts-base.md)。目录职责见 [afts-architecture.md](afts-architecture.md)。本模板用到的 Tool / Skill / MCP 见 [afts-workcase-fx-capabilities.md](afts-workcase-fx-capabilities.md)。

## 题目

定义第一个 workflow 模板：用户说要研究哪个外汇交易对，Agent 团队完成研究并产出一个 ML 模型，模型上线后对新 K 线给出预测区间，在看板上与真实走势对照。

模板不绑定某个交易对。EUR/USD、USD/JPY 只是验证用例。

## 交付物

一个 Project 交付一个**策略包**：

1. 带版本的模型产物（权重、特征代码快照、模型卡）。
2. 实验台账（所有实验，含失败的）。
3. 锁定考场上的评分。
4. 上线后每根新 K 线的预测区间，以及与真实价格的对照。

Session 层的每日或阶段简报是附带产出，不是交付核心。

## 原则

- **谁产出，谁不当裁判。** Agent 可以开发数据处理、特征和模型，不能修改评估层（考场）。
- **预测只追加，永不重算。** 只有事先写下的预测才算数。
- **报告里的每个数字都要有 Run ID。** 没有出处的数字算违规。
- **Agent 推理不进快循环。** 上线后的预测是纯数值计算，不调用 LLM。

## 模板参数

Main 从对话里填参数，缺的补问用户。

| 参数 | 取值 | 默认 |
| --- | --- | --- |
| 交易对 | 一个或多个，如 `EURUSD` | 无，必须给 |
| 频率 | `1h`、`1d` | 无，必须给 |
| 预测期 | 下 1 根 K 线 | 下 1 根 |
| 覆盖率目标 | 0–1 | 0.90 |
| 数据范围 | 起止日期 | 用导入数据的全部范围 |
| 数据来源 | 用户导入（路径或对话框） | 用户导入 |
| 研究预算 | 最大实验次数、token / 费用上限 | 待定 |

## 固定与动态

| 固定在模板里 | 由 Agent 动态决定 |
| --- | --- |
| 阶段与顺序、关卡位置 | 每个阶段内怎么做、派几个 Subagent |
| Project 目录约定与读写权限 | 用什么检验、什么特征、什么模型 |
| 考场规则（切分方式、成本模型、指标） | 超参数、特征组合 |
| git 操作只由 Main 执行 | 研究方向、汇报内容 |

考场规则在模板里，具体取值随参数生成（如小时线与日线的切分窗口、各交易对的点差），生成后对该 Project 锁定。

## 一级 Agent

| 角色 | 职责 | 主要产出 |
| --- | --- | --- |
| Main | 解析参数、套用模板、建 Project、关卡验收、git 提交、处理插话、汇总 | `project.yaml`、提交、简报 |
| 数据工程师 | 导入、解压校验、清洗、对齐时区与 K 线 | `data/raw`、`data/processed`、清洗报告 |
| 宏观/央行研究员 | 利差、政策周期等宏观特征候选 | 特征候选说明 |
| 新闻/事件研究员 | 经济日历事件、央行讲话鹰鸽打分，作为每日信号 | `signals/` |
| 量化/策略分析师 | 价格类特征、研究迭代、候选模型 | `experiments/`、候选模型 |
| 风控/审查员 | 查泄漏、过拟合、成本敏感性，挑考场的毛病 | 审查意见 |

研究员只提特征候选，量化分析师决定采用哪些（待用户确认）。

## 主流程

```text
[Main] 解析参数 → 套用模板 → 建 Project + git init → 提交
  │
阶段1 导入      数据工程师：inbox → Sandbox 解压校验 → data/raw + 来源记录
阶段2 清洗      数据工程师：data/processed + 清洗报告
  🚧 关卡A      用户在 Data Explorer 接受或要求修改 → Main 提交
阶段3 研究      宏观、新闻、量化并行 → 特征候选、signals/
阶段4 建模      量化分析师：研究迭代回路 → 候选模型
阶段5 审查      审查员：审查意见
阶段6 终考      系统（不是 Agent）用锁定考场在测试段跑一次
  🚧 关卡B      用户看分数和审查意见：批准或驳回
阶段7 注册上线  Main：models/vNNN + tag + 改 project.yaml → 提交
  │
快循环（见「上线后」）
```

关卡只设 A、B 两处，还是每阶段都要确认：待用户决定。

### 单 Agent 回路（Harness）

组装上下文（角色设定 + 任务 + 按需 Skill + 文件路径而非全文）→ 模型调用 → 权限检查（工具、目录）→ 执行工具（Python 走 Runner，带 Job ID）→ 结果压缩后回给模型 → 停止条件：产物符合契约 / 预算用完 / 失败次数到上限 / 需要提问。

### 研究迭代回路（量化分析师）

提方案 → Sandbox 训练 → 考场**验证段**打分 → 写台账 → 比基准好且预算够则继续，否则选出最好的候选交审查。

Agent 只看得到验证段分数，测试段只在阶段 6 由系统跑一次。

## Project 目录

位置：`storage/projects/<id>/`。每个 Project 是一个独立 git 仓库。`storage/projects/` 应进入 AFTS 自身的 `.gitignore`（施工时再改）。

```text
<id>/
├── project.yaml        # 模板参数、当前上线的模型 tag
├── inbox/              # 用户导入的原件，不解压
├── data/
│   ├── raw/            # 只追加
│   └── processed/
├── signals/            # 新闻 Agent 的每日信号，带 Agent 版本
├── eval/               # 考场：切分、成本、指标
├── experiments/<run_id>/
├── models/vNNN/        # weights/、features.py、card.md
├── predictions/        # 时间、点预测、下界、上界、模型版本
└── reports/
```

### 读写权限

| 目录 | 可写者 | 规则 |
| --- | --- | --- |
| `inbox/` | 系统导入流程 | 原样存放，记哈希 |
| `data/raw` | 数据工程师 | 只追加 |
| `data/processed` | 数据工程师 | 新版本不覆盖旧版本 |
| `signals/` | 新闻研究员 | 只追加，不补写历史 |
| `eval/` | 仅用户 | Agent 只读 |
| `experiments/` | 量化分析师 | 失败的也保留 |
| `models/` | 量化分析师提交，用户批准 | 注册后不可改 |
| `predictions/` | 快循环定时任务 | 只追加，永不重算 |
| `project.yaml` 的上线版本 | 仅用户 | 等同部署开关 |

Agent 的文件工具限定在 Project 根目录内，按角色校验读写。落在 `tools/` 与 `harness/policies`。

## git 规则

- 只有 Main 执行 git 操作。其他 Agent 只写文件。
- Main 在关卡和里程碑处提交：任务被接受、模型注册、上线版本切换。提交信息结构化，含任务 ID、Agent、产物路径。
- 模型版本用 tag，如 `model/v003`。
- 返工是新提交，旧提交保留。
- 进 git：代码、配置、`project.yaml`、台账、模型卡、预测、报告。不进 git：原始数据与权重本体，只记哈希清单。
- Main 禁止：`reset --hard`、强推、改写历史、推送远程。回退只用 `git revert`，并需用户确认。

## 数据导入

两条入口，都先到 `inbox/`：

- **用户指定路径**：复制进来，不链接原文件。
- **对话框粘贴或拖入**：自动存成文件，记下来自哪一轮对话。内容过大时，Main 提示改用路径导入。

之后数据工程师在 Sandbox 里解压、校验列与格式、对齐时区，写入 `data/raw`，附来源记录（来源、日期、哈希、条款备注）。压缩包须防路径穿越、解压炸弹、夹带可执行文件。

## Agent 通信

- 不允许自由聊天。消息有类型：`task`、`result`、`question`、`review`。
- 消息只传引用，内容写在 Project 文件里。
- 每条消息经 Workflow 登记，作为事件进 observability。看板的 Team Overview、Agent Activity 由这些事件生成。

## 返工

每个产物记下依赖的上游版本。用户否决某个产物时：

1. 意见作为 `review` 消息发给产出它的 Agent。
2. Agent 返工，产出新版本。旧版本及其下游保留，供对比。
3. Main 按依赖标出过期的下游，询问用户是否重跑。只重跑那一支。

关卡 B 驳回时回到阶段 4，审查意见带进量化分析师的上下文。考场分数记录所用数据版本，数据版本不同的分数不直接比较。

## 用户插话

用户消息只进 Main。Main 分类处理，拿不准时先问用户。

| 类型 | 处理 |
| --- | --- |
| 提问 | 读状态与产物直接回答，流程不停 |
| 小调整 | 加任务或调计划，运行中的任务继续 |
| 方向变化 | 在下一个安全点（节点之间，不在工具执行中）暂停，重新规划，告知会取消哪些任务 |
| 暂不做的想法 | 记入 Project Memory 待议清单 |

## Main 唤醒条件

阶段完成、异常、到达关卡、用户消息、本地资源告警、API 预算告警。其余时间不占用模型调用。

## 资源控制

所有模型都走 API。

### 本地资源：只管 Python 任务

- 监控 RAM、CPU、磁盘与各 Python 进程（评估复用 Hermes 的资源监控）。
- 按任务类型预估占用，每次运行后记录实际峰值以修正预估。
- 准入控制：预估后仍低于上限才放行，否则排队。为用户机器保留空闲 RAM（比例待定）。
- 优先级：快循环 > Main 回应用户 > 普通阶段任务 > 研究迭代训练。
- 紧张时：先停止放行 → 再拒绝新的派生请求 → 内存将尽时才终止最低优先级任务。被终止的任务标记为「因资源终止」，用同一 Job ID 重试。macOS 上以监控加超时为主，不依赖进程硬内存上限。

### API 资源：管 Agent 与 Subagent

- 全局共享一个限速器，按提供方的请求数与 token 限额排队。
- 429 退避重试，对 Agent 透明；持续失败才作为错误上报。
- token / 费用预算分层：Project、阶段、一级 Agent。
- Subagent 派生配额由 API 并发余量与该 Agent 剩余预算决定。拒绝原因作为工具结果返回，Agent 可改为串行。

配额写在配置里，Agent 不能修改。看板资源面板分本地与 API 两块。

## 考场与比较

考场只用业界公认的方法，清单见能力文件中的 `eval-standards` Skill。

- **历史比较（上线前）**：在锁定测试段做 walk-forward，决定能否注册。
- **前向比较（上线后）**：T 时写下对 T+1 的区间，T+1 真实 K 线到达后对照。看板显示区间带、真实价格、滚动覆盖率与宽度。
- **衰退**：滚动覆盖率低于阈值时唤醒 Main，提醒用户是否重训；同意则回到阶段 4。

## 上线后（快循环）

新 K 线到达 → 定时任务运行当前上线模型 → `predictions/` 追加 → 对照上一条预测 → 更新看板 → 必要时触发衰退提醒。

## 待用户决定

1. 关卡只设 A、B 两处，还是每阶段都确认。
2. 研究员只提特征候选、由量化分析师决定采用，是否确认。
3. 关卡 B 驳回后，下一个候选是换一段新的测试数据，还是沿用并在台账记下考试次数。
4. **架构缺口**：快循环需要定时调度，当前架构没有调度层。讨论中的方案（未确认）：
   - 三种触发共用一个 `advance` 操作：拉新 K 线 → 对每根尚无预测的 K 线，用当时在线的模型版本、只用其之前的数据算区间 → 写入并对照 → 更新覆盖率。
   - 第一版：手动「推进」按钮 + 打开 Project 时补到最新。用户指定 Project 的定时自动执行后置。
   - 每条预测标 `live` 或 `catchup`，看板与前向评估分开统计。依赖 LLM 信号的特征不能补算，只用当时记录的信号，缺失即标缺失。
   - 自动执行的位置：`backend/execution` 内加定时组件（倾向），或新建 `backend/scheduling`（需用户批准）。Mac 睡眠时不执行，醒后靠补算追上。
5. 前向比较所需的新 K 线：用户倾向接免费 API。Yahoo / yfinance 已因条款排除。候选（条款与额度均未核对）：OANDA 模拟账户 API、Twelve Data、Alpha Vantage、Dukascopy、FRED / 欧洲央行参考汇率（仅日线）。接法：新工具 `fx_fetch` 把结果放进 `inbox/`，走与手动导入相同的流程；不经 LLM；API key 只在环境变量；数据源可替换。
6. 大文件（原始数据、权重）在 git 之外放在哪里。
7. 资源阈值、预算默认值、衰退阈值。

## 建议施工顺序（未确认）

1. 纯 Python 纵向薄切：导入 → 清洗 → 基准区间模型 → 考场评分。不碰 Java 与 Agent。
2. 单轮 Harness：一个 Agent 调一个工具（如跑一次考场）。
3. 一个 Agent 在固定菜单内做研究迭代：出方案、考场打分、台账记录。
4. 团队、新闻信号、看板区间图、快循环。

每一步另开施工计划。

## 完成定义（模板整体）

- 用同一模板跑两组参数（如 EUR/USD `1h` 与 USD/JPY `1d`），两次都走完阶段 1–7。
- 每个 Project 目录符合约定，git 历史中可见各关卡提交与模型 tag。
- 考场给出两组参数的覆盖率与宽度，台账含全部实验。
- 看板显示两者的预测区间与真实价格对照。
- 演示一次返工：否决清洗结果后，只有下游被标记过期并重跑。

## 不做

- 高频交易、日内 tick 级策略。
- 真实下单。Agent 不接券商或交易接口。
- 本地 LLM。
- 第一版不接 MCP 与外部数据源。
- 在本文件锁定类名、接口签名或存储技术。
